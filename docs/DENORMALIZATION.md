# 스터디픽 역정규화 검토

강의 481~483쪽은 정규화에 따른 조인 증가와 응답 시간의 관계를 설명하고, 성능 요구 때문에 중복을 허용할 때 갱신 이상과 무결성 관리 비용도 검토하도록 한다. **역정규화를 반드시 적용해야 한다는 뜻은 아니다.**

현재 12개 테이블을 유지한다. 이번 문서화에서는 테이블 병합이나 DB 구조 변경을 하지 않는다. 성능 향상 수치는 측정한 적이 없으므로 단정하지 않으며, 아래는 기존 저장 결정의 필요성과 관리 방법을 검토한 결과다.

| 검토 대상 | 분류 | 검토 결과와 이유 | 중복 또는 보존에 따른 관리 |
| --- | --- | --- | --- |
| MEMBER.point_balance | 집계값 중복 저장 | 유지. POINT_HISTORY.delta 합계로 구할 수 있지만 매번 내역을 합산하지 않고 잔액을 조회하기 위한 저장값 | 잔액·내역을 같은 트랜잭션에서 변경하고 잔액이 0 이상인지 검사. 회원별 잔액과 내역 합계의 SQL 대조 필요 |
| RESERVATION_SLOT.seat_id | 무결성을 위한 중복 저장 | 유지. 예약의 seat_id로 유도할 수 있지만 (seat_id, slot_start) PK로 좌석·시간 중복 점유를 직접 차단 | 예약과 시간대의 좌석 일치는 두 개의 독립 FK만으로 보장되지 않는다. 함께 삽입·변경하고 연결 SQL로 일치 여부 검사 |
| REVIEW.cafe_id | 조회·이력 보존용 저장 | 유지. 예약이 연결된 후기는 예약→좌석→카페로 조회할 수 있으나 카페별 후기 조회와 예약 연결 없는 후기 저장도 고려 | 예약이 연결된 행에서는 후기의 회원·카페가 해당 예약과 일치해야 한다. FK는 참조 행의 존재만 검사하므로 별도 일치 검사 필요 |
| PAYMENT.amount | 예약·결제 사이의 금액 저장 | 유지. 결제 금액과 환불액을 결제 기록으로 관리한다. PAID 예약 변경 시 예약 금액과 결제 금액을 함께 갱신 | PAID 결제와 예약 금액을 SQL로 대조하고, 환불액은 0 이상·결제액 이하 CHECK 적용 |
| RESERVATION.total_price | 예약 당시 확정 금액 보존 | 유지. 현재 PRICE_PLAN.price에서 매번 다시 계산하면 과거 예약 금액이 달라지므로 확정 금액을 저장 | 현재 요금과 값이 달라도 곧바로 오류가 아니다. 성능을 위한 역정규화와 구분하고 예약 변경 정책에 따라 갱신 |
| 지역 이름·좌석 유형 설명의 병합 | 테이블 병합 후보 | 추가 적용하지 않음. REGION·SEAT_TYPE을 별도로 유지하고 번호로 참조 | 중복 갱신과 설명 불일치를 줄임. 조인이 느리다는 실측 없이 테이블을 합치지 않음 |
| 평균 요금·차액·평점 집계 저장 | 집계 테이블·뷰 후보 | 추가 저장하지 않음. 요금·후기에서 조회 시 계산하며 평균 대비 표시·정렬은 유지 | 화면의 지역 평균은 같은 지역·좌석 유형·이용권의 등록 요금으로 계산하며 EXAMPLE 요금도 포함한다. 서버 목록·상세의 검증 요금 비교는 VERIFIED 시간당 요금만 집계한다. 평균 대비 표시·정렬은 유지하며 별도 뷰는 만들지 않는다. |

**정규형과의 구분:** 계산 가능한 값을 저장하거나 테이블을 나누지 않았다는 사실만으로 자동으로 3NF·BCNF 위반이 되지는 않는다. 정규형은 한 릴레이션 안의 후보키와 함수 종속으로 판정한다. 기존 11개 BCNF·예약 시간대 3NF 분석은 문서에 선언한 업무 규칙을 전제로 하며, NULL 허용 UNIQUE와 예약이 연결된 후기의 부분집합 규칙도 구분한다.

### 데이터 일치 관리와 검증 기록

- 2026-11-26: GitHub main의 스키마·소스와 문서 구성을 대조하고 모델 검사를 다시 실행하였다. **이번에는 운영 DB의 실시간 데이터 검사를 다시 실행하지 않았다.**
- SQL 정합성 결과는 데이터 상태의 증거이며, 정규형 판정을 대신하거나 성능 개선을 입증하지 않는다.
