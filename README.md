# 스터디픽 (스터디카페 통합 예약·비교)

데이터베이스설계 팀 프로젝트. 시·구 평균 요금과 비교하며 스터디카페를 찾고 좌석을 예약하는 웹사이트입니다.

배포 주소: https://studycafe-tan.vercel.app (이 저장소의 `main`에 머지하면 Vercel이 자동으로 다시 배포합니다)

## 구조

| 경로 | 설명 |
|---|---|
| `public/` | 프런트엔드 (정적 사이트). `index.html`, `style.css`, `app.js`, `data.js` |
| `public/data.js` | 샘플 카페 18곳 (가상 데이터) |
| `server/index.js` | 운영 화면의 가입·로그인·예약·좌석 조회를 처리하는 Express/MySQL API |
| `index.js`, `vercel.json` | Vercel Express 진입점과 배포 설정 |
| `test/` | 예약 충돌·장애 복구·목록 좌석 조회 회귀 테스트 (`npm test`) |
| `db/schema.sql`, `db/seed.sql` | MySQL 스키마와 더미 데이터 |
| `scripts/` | DB 초기화, 카카오 장소 수집 |

## 실행

프런트만 보기 (DB 불필요):

```
npx serve public
```

서버 + DB 포함 (MySQL 필요):

```
npm install
cp .env.example .env   # DB 접속 정보 입력
npm run db:init
npm start              # http://localhost:3000
```

## 참고

- 운영 사이트는 Vercel API와 Aiven MySQL을 사용합니다. DB 연결·환경 변수·감시 구성은 [인터넷 DB 설정](docs/HOSTED_DB.md)을 참고하세요.
- 정적 프런트만 실행하면 샘플 데이터와 브라우저 저장소 모드로 동작합니다.
- `.env`(DB 비밀번호, 카카오 키)는 저장소에 올리지 마세요. `.gitignore`에 포함돼 있습니다.
- 실제 카페의 이름·주소·위치는 카카오 장소 정보입니다. 가격·좌석 수·사진은 예시이며, 잔여석은 이 사이트에 저장된 예약을 기준으로 계산합니다.
- 운영 DB에서 `db:init -- --force`를 실행하면 기존 프로젝트 데이터가 삭제됩니다. 일반 실행·배포·복구 과정에서 초기화하지 마세요.
- 스터디카페 선별 기준과 누락 22개 지역의 확인 결과는 [카페 데이터 점검](docs/CAFE_AUDIT_20261103.md)에 기록했습니다.
- `npm test`는 DB 자격 증명 없이 실행되며, PR과 main 변경 시 GitHub Actions에서도 실행합니다. 줄바꿈은 `.gitattributes`로 LF(Windows 실행 파일은 CRLF)를 유지합니다.

## 설계 모델과 ERD

- 브라우저 뷰어: `/erd/` (개념적 ERD, 개체별 속성, 논리적 릴레이션)
- 현재 구성: 개체 12개, 관계 15개, 테이블 12개, 속성 84개, 외래키 15개, 뷰 없음
- `npm run check:model`: SQL 스키마와 ERD 문서·뷰어의 이름·타입·NULL·키 및 모델 구성을 대조합니다. 운영 DB에 접속하지 않습니다.
- 전체 관계도는 키 속성만 또는 전체 속성으로 전환하고 SVG·PNG로 저장할 수 있습니다.

## 데이터베이스 설계 과정

강의자료의 설계 단계에 맞춰 요구사항을 정리하고, 개념적 모델을 릴레이션으로 변환한 뒤 정규화·역정규화 검토와 물리적 설계를 진행했습니다. 아래는 최종 보고서와 현재 구현을 기준으로 정리한 과정입니다.

### 1. 요구사항 분석과 범위 확정

회원 관리, 이용 옵션 선택, 지역 설정, 스터디카페 비교·추천, 고객 예약으로 업무를 나누고 각 기능에 필요한 데이터와 트랜잭션을 정리했습니다. 좌석 선택부터 예약·결제·포인트·후기까지 연결하되, 카페 찜과 시설별 관리·검색, 소셜 로그인, 사장·관리자 기능은 최종 범위에서 제외했습니다. 지역 평균 대비 요금 표시와 정렬은 유지하며, 역·대학 근처 검색은 카카오 장소 검색과 화면 계산을 사용하고 별도 테이블을 두지 않았습니다.

### 2. 개념적 설계

회원, 휴대폰 인증, 지역, 카페, 좌석 유형, 좌석, 요금제, 예약, 예약 시간대, 결제, 포인트 내역, 후기의 12개 개체와 15개 관계를 정리했습니다. Chen 표기법의 사각형·마름모·타원으로 개체·관계·속성을 표현하고, 관계의 대응 수와 참여 조건을 표시했습니다. 예약 시간대는 좌석에 종속되는 약한 개체로 표현하고, 휴대폰 인증은 회원 생성 전의 임시 기록이므로 회원과 직접 FK 관계를 만들지 않았습니다.

개념적 ERD에서는 업무상의 관계와 식별 속성을 설명하고, 자료형·NULL·키의 구체적인 명세는 논리적 릴레이션과 물리적 설계서에서 구분해 제시했습니다. [개념적 ERD·논리적 모델 뷰어](https://studycafe-tan.vercel.app/erd/)에서 확인할 수 있습니다.

### 3. 논리적 설계

개체와 관계를 12개 테이블, 84개 컬럼으로 변환하고 기본키·후보키·외래키와 NULL 허용 여부를 정했습니다. 지역·카페, 카페·좌석, 회원·예약 등의 1:N 관계는 N쪽 테이블의 외래키로 연결하고, 예약·결제는 결제의 `reservation_id`에 NOT NULL·UNIQUE·FK를 두어 예약당 결제 행을 최대 하나로 제한했습니다.

예약 시간대의 기본키는 `(seat_id, slot_start)`로 정해 같은 좌석·같은 시간 칸의 중복 저장을 막았습니다. 이 기본키만으로 임의의 예약 구간 겹침이나 예약과 시간대의 좌석 일치까지 보장되는 것은 아니므로, 서버의 좌석 행 잠금·시간 겹침 검사와 별도 정합성 검사를 함께 사용합니다. 관계와 테이블 구성은 [릴레이션 ERD](db/ERD.md), 실제 키·제약 정의는 [SQL 스키마](db/schema.sql)에 정리했습니다.

### 4. 정규화

| 단계 | 적용·검토 내용 |
|---|---|
| 제1정규형(1NF) | 한 카페의 여러 좌석을 한 칸에 나열하는 구조 대신 `SEAT`에 좌석별 한 행을 두고 각 컬럼에 단일 값을 저장했습니다. |
| 제2정규형(2NF) | 후보키 일부에만 종속되는 비주요 속성이 있는지 검토했습니다. 카페 설명과 좌석 유형 설명은 각각 `CAFE`, `SEAT_TYPE`에 두고 번호로 참조하며, 복합키를 쓰는 예약 시간대도 부분 함수 종속 여부를 따로 확인했습니다. |
| 제3정규형(3NF) | 지역 설명은 `REGION`, 좌석 유형 설명은 `SEAT_TYPE`에 두어 다른 테이블에 반복 저장하지 않았습니다. 예약·결제·포인트 내역·후기는 각 업무의 키가 해당 속성을 결정하도록 검토했습니다. |
| BCNF | 선언한 업무 규칙과 함수 종속을 기준으로 11개 릴레이션은 BCNF, `RESERVATION_SLOT`은 3NF로 분석했습니다. 데이터 중복이 현재 없다는 사실만으로 정규형을 판정하지 않았습니다. |

`RESERVATION_SLOT`에는 한 예약이 한 좌석만 사용한다는 업무 규칙에 따라 `reservation_id → seat_id`가 성립합니다. 후보키는 `(seat_id, slot_start)`와 `(reservation_id, slot_start)`이며, `reservation_id` 자체는 슈퍼키가 아니므로 BCNF에는 해당하지 않습니다. 모든 속성이 후보키에 포함되는 주요 속성이므로 3NF는 만족합니다. 두 번째 후보키의 유일성은 별도 UNIQUE가 아니라 기본키와 예약별 좌석 일치 규칙을 전제로 하며, 서버 처리와 SQL 검사로 확인합니다. 좌석·시간의 중복 점유를 직접 차단하는 복합 기본키를 유지하기 위해 이 구조를 선택했습니다.

### 5. 역정규화와 중복 저장 검토

`MEMBER.point_balance`는 내역 합계를 매번 계산하지 않고 조회하기 위한 집계값으로, `RESERVATION_SLOT.seat_id`는 좌석·시간 중복을 기본키로 막기 위한 중복 속성으로 유지했습니다. `REVIEW.cafe_id`는 카페별 조회와 예약 연결 없는 후기 저장을 고려했으며, 예약이 연결된 후기는 해당 예약의 회원·카페와 일치하는지 검사합니다.

`RESERVATION.total_price`는 현재 요금으로 다시 계산하지 않는 예약 당시 확정 금액이고, `PAYMENT.amount`는 결제 기록이므로 성능 목적의 중복 저장과 구분했습니다. 관련 변경은 기능별 트랜잭션에서 처리하고 잔액·내역 합계와 예약·결제 금액을 SQL로 대조합니다. 추가 테이블 병합, 평균·평점 집계 테이블, 뷰는 만들지 않았으며 성능 향상 수치는 측정하지 않았습니다. 판단 근거는 [역정규화 검토서](docs/DENORMALIZATION.md)에 정리했습니다.

### 6. 물리적 설계와 구현

MySQL 8.4·InnoDB를 기준으로 자료형, 기본값, NOT NULL, PK·UNIQUE·FK·CHECK, 참조 동작과 조회 인덱스를 명세했습니다. 예약 생성·변경은 관련 좌석을 잠그고 시간 겹침을 검사한 뒤 예약·시간대·결제와 필요한 포인트 변동을 하나의 트랜잭션으로 처리합니다. 취소 시에는 점유 시간대를 해제하고 환불과 포인트를 함께 반영합니다.

[물리적 설계서](docs/PHYSICAL_DESIGN.md)는 SQL·ERD 모델에서 생성하며, [웹 설계서](https://studycafe-tan.vercel.app/design/)에서도 확인할 수 있습니다. 휴대폰 문자와 외부 결제는 실제 발송·청구가 없는 모의 처리이며, 예약과 포인트의 DB 변경은 실제 트랜잭션으로 수행합니다.

### 7. 설계·구현 검증

SQL 스키마, ERD 문서, 뷰어, 물리적 설계 명세를 대조하고 예약 충돌·장애 복구 등을 자동 테스트했습니다. 최종 보고서에 반영한 소스 기준은 `042e22c`이며, 해당 버전의 자동 테스트 41개를 통과했습니다. README 보완은 이후 문서 변경으로 구분합니다.

2026년 11월 26일 12:01~12:02(한국 시간)에는 운영 Aiven DB를 인증서 검증 TLS와 읽기 전용 트랜잭션으로 직접 조회하고 ROLLBACK으로 종료했습니다. 이 재검증에서는 초기화·스키마 변경·데이터 보정을 실행하지 않았습니다.

| 검사 | 확인 결과 |
|---|---|
| 운영 스키마 | MySQL 8.4.11, 테이블 12개, 컬럼 84개, PK 12개, UNIQUE 9개, FK 15개, CHECK 10개, 뷰 0개 |
| 설계와 구조 대조 | 컬럼·자료형·NULL·기본값·키·참조 동작 등의 기능상 불일치 0건 |
| 인덱스 | 명시적 보조 인덱스 17개 일치. 운영 DB에는 FK 유지용 자동 인덱스 3개가 더해져 보조 인덱스 총 20개 |
| FK 이름 차이 | 예약 시간대 FK 2개에 `_compact` 접미사가 있으나 참조 대상·동작은 동일. InnoDB의 NO ACTION과 RESTRICT는 동등한 동작으로 대조 |
| 데이터 정합성 | 기존 11개 검사, FK 15개 참조 누락 검사, 예약 구간·슬롯·취소·환불·평점·요금 출처의 추가 7개 검사 모두 불일치 0건 |

검증 결과는 해당 시점의 상태이며 정규형 판정이나 성능 측정을 대신하지 않습니다. 원본 결과인 `live-schema-audit-20261126.json`과 `live-consistency-audit-20261126.json`, 상세 스키마 검사 스크립트는 제출용 ZIP의 `verification/`에 포함했습니다. 이전 11월 23일 보정 내역과 이번 읽기 전용 재검증은 구분합니다.
